wscanfd: an open Linux driver for the Waveshare USB-CAN-FD

The Waveshare USB-CAN-FD (non-B model, SKU 25029, USB ID 04d8:0053) is a two-channel, isolated CAN FD adapter. The vendor supports this model on Windows only. This project provides a native SocketCAN kernel module (wscanfd.ko) and a Python/libusb userspace driver with a SocketCAN bridge.

1. Overview & status

The adapter has an NXP LPC54616 microcontroller with two on-chip MCAN CAN FD controllers. It is a vendor-specific USB device with plain bulk endpoints, so it can be driven by a kernel driver or from userspace through libusb.

  • Userspace driver (wscanfd/): Python + pyusb. CLI (info, dump, send, bridge), a Python API, and a bridge to a vcan interface so that standard SocketCAN tools work. Tested on hardware.
  • Kernel driver (kernel/): an out-of-tree SocketCAN module, wscanfd.ko (DKMS-ready). It creates can0/can1, is configured with ip link, and paces TX to work around the firmware's missing flow control. Tested on hardware. Section 6.

Status

Tested against a LilyGo T-2CAN-FD running the project's t2can-echo/ firmware (MCP2518FD port for CAN FD, ESP32 TWAI for classic CAN). See section 7.

Quick start

Kernel driver (recommended):

make -C kernel && sudo modprobe can-dev && sudo insmod kernel/wscanfd.ko
sudo ip link set can0 type can bitrate 500000 sample-point 0.8 dbitrate 2000000 fd on
sudo ip link set can0 up && candump can0

Userspace driver (no kernel module):

python3 -m venv .venv && .venv/bin/pip install pyusb pytest
sudo install -m 644 udev/70-wscanfd.rules /etc/udev/rules.d/ && sudo udevadm control --reload
# replug the adapter, then:
.venv/bin/python -m wscanfd info
.venv/bin/python -m wscanfd dump -c both -b 250000

Channel 0 is the connector labelled CAN1, channel 1 is CAN2.

Architecture

There are two ways to get frames from applications to the bus. The kernel module is a normal SocketCAN driver. As an alternative that needs no kernel module, the userspace bridge copies frames between a virtual vcan interface and the adapter through libusb. Both paths speak the same USB protocol to the adapter's firmware.

3. Protocol reference

All multi-byte fields in the command framing and in command payloads are big-endian. The exception is the RX records on EP 0x82/0x83: they are raw MCAN RX buffer elements and are little-endian. The reference implementation is wscanfd/protocol.py (and kernel/wscanfd.c), and tests/test_protocol.py checks it against known-good byte sequences.

3.4 Session sequence

wscanfd follows this order: claim interface 0 (without SET_CONFIGURATION, see quirks), drain EP 0x81, open handshake, device info. Then, for each channel: InitCAN, clear the filter, drain the RX endpoint, StartCAN, and start an RX reader. To stop a channel it sends ResetCAN. Closing the device sends CloseDevice.

3.8 Bit-timing words

The abit and dbit words carry the raw fields of the MCAN NBTP/DBTP registers, each stored as value − 1, packed into a big-endian 32-bit word. With the 60 MHz MCAN clock, any bitrate can be computed.

Formulas: TQ per bit = 1 + TSEG1 + TSEG2. Bitrate = 60 MHz / (BRP × TQ per bit). Sample point = (1 + TSEG1) / (TQ per bit). TSEG1 includes the propagation segment.

3.11 RX records (EP 0x82 / EP 0x83)

Received frames arrive unframed on the channel's bulk-IN endpoint. Each record begins with the two header words of an NXP MCAN RX buffer element (R0, R1, both little-endian). One transfer can contain several records back to back, for example a 63-byte transfer holding three classic records. A record is classic or FD depending on R1.FDF. An idle poll returns 8 zero bytes, which is not a record.

  • ID: if XTD = 1, ID = R0[28:0]. Otherwise ID = R0[28:18]. For standard frames the low 18 bits of R0 are not zero in practice (for example R0 = 0x1F800FC0 for ID 0x7E0), so mask them off.
  • Length: classic: min(DLC, 8). FD: the DLC maps to 0-8, 12, 16, 20, 24, 32, 48, 64. RTR frames carry no data.
  • Timestamp: 32-bit LE at offset 17 (classic) or 72 (FD), in 100 µs ticks.
  • Telling records apart: read R1, check FDF to pick 21 or 76 bytes, and for classic records check that byte 16 is 0x55. An 8-byte all-zero transfer is an idle poll.
  • No error frames or status records ever appear on these endpoints.

Worked example: the test vector 48029004 000008ff fffefdfcfbfaf9f8 55 43d86300 decodes as R0 = 0x04900248, giving std ID (R0 >> 18) & 0x7FF = 0x124. R1 = 0xFF080000, giving DLC 8, FDF 0, FIDX 0x7F, ANMF 1. Data FF FE FD FC FB FA F9 F8, marker 0x55, timestamp 0x0063D843 × 100 µs. This is the peer's echo of TX 0x123 00..07: ID + 1, data XOR 0xFF.

3.12 0x800D GetStatus (diagnostic only)

Request 55 0D 29 dev ch 00 00 00, reply 64 bytes. The meaning of the fields was inferred from their behaviour on hardware:

BytesContent
0channel
2"started"? flag
4-7looks like MCAN ECR, LE: TEC [7:0], REC [14:8], RP [15], CEL [23:16]
8-11looks like MCAN PSR, LE: LEC [2:0], ACT [4:3], EP [5], EW [6], BO [7], DLEC [10:8], TDCV [22:16]

This is a stale snapshot, not a live register. TEC = 128 and CEL = 128 appeared during a no-ACK episode, but the values freeze, and TEC reads 0 while the adapter is still retransmitting. A request for channel 1 returned channel 0's counters. Use it only as a hint. tools/status_probe.py records it through bus-error scenarios.

3.13 Unused and dangerous commands

Never send 0x8006 (firmware update). It presumably puts the adapter into its bootloader. Nothing in this project sends it.

0x8007/0x8008 (get/set user serial number) and 0x800C (ClearBuffer, 8-byte payload) exist but are not used by this driver.

4. Firmware behaviour & limitations

SET_CONFIGURATION wedges the firmware

A second SET_CONFIGURATION sent to an already-configured device (for example pyusb's dev.set_configuration()) makes the firmware stop replying on EP1 IN until it is power-cycled. A USB reset does not help. wscanfd only sets a configuration if none is active. The kernel driver must never call usb_reset_configuration() or usb_set_configuration().

Idle RX polls return 8 zero bytes instead of NAKing

When there is no data, the RX endpoints complete every bulk-IN request immediately with 8 zero bytes. A "read until timeout" drain loop therefore never ends, so bound drains by time (wscanfd uses 100 ms). A naive URB resubmit loop also spins at a very high completion rate. The kernel driver re-arms idle URBs through an hrtimer (idle_poll_us, default 1 ms, 6.4).

No TX flow control: excess frames are silently dropped

The adapter buffers only about 10 TX frames. When the buffer is full it keeps completing USB writes and silently drops the excess. In the bench test, a kernel burst of 2000 frames written as fast as USB accepted them put only 50 on the wire. Pacing below the bus frame time loses frames; pacing at or above it loses none.

On top of that, the firmware costs about 300 µs + 2 µs per data byte per frame, whatever the bit rate: 0-16 bytes is fine at 300 µs, 32 bytes needs 350 µs, and 64 bytes needs 400 µs. That caps throughput at about 3300 short frames/s even at 1 Mbit/s. Received frames use the same budget: with a 1:1 echo load, TX needed about twice the per-frame floor.

The kernel driver handles this with a device-queue model (6.3). The userspace driver applies the same model in USBCANFD.send(), which blocks while the estimated device queue is full (2000 frames at 1M/5M, mixed 64-byte FD+BRS and classic, 2000/2000 delivered). Its earlier unpaced 1000-frame test at 250k passed because each synchronous USB write took longer than a bus frame.

No TX confirmation; unacknowledged frames are retried, then silently dropped

0x8004 gets no reply, and no TX-complete or TX-failed message ever arrives later. If nobody ACKs, the adapter retransmits (about 2000 attempts, about 0.5 s, observed at 500k) and then silently drops the frame. The channel recovers by itself afterwards and does not need a host reset. "Sent" can therefore only ever mean "accepted by the adapter".

No error or bus-state information

No error records appear on the RX endpoints. 0x800D is a stale snapshot (3.12). Bus state can only be estimated.

Smaller gotchas

  • CAN FD with BRS needs the same nominal sample point on all nodes. With the kernel's default (87.5 %) against an 80 % peer, BRS frames fail. Use sample-point 0.8 (details).
  • Termination flag is a no-op. InitCAN byte 30 bit 0x40 does nothing. Use the physical switches.
  • Standard-ID records have junk in R0[17:0]. Mask the ID.
  • The 0x800D reply for channel 1 contained channel 0's counters.
  • One unexplained first-run failure. The very first TX run after the peer was flashed got nothing through. All later runs worked. Watch for "first StartCAN after power-up" problems.
  • Permissions. The /dev/bus/usb node is root-only by default, so the userspace driver needs the udev rule (details). The kernel driver doesn't.

5. Userspace driver (wscanfd/)

A pure-Python driver built on pyusb/libusb. protocol.py holds the wire formats as pure functions, device.py does the USB I/O, bridge.py implements the SocketCAN bridge, and __main__.py is the CLI. The only runtime dependencies are pyusb.

5.1 Install

python3 -m venv .venv && .venv/bin/pip install pyusb pytest
sudo install -m 644 udev/70-wscanfd.rules /etc/udev/rules.d/ && sudo udevadm control --reload
# then replug the adapter
.venv/bin/python -m pytest tests          # protocol tests against known-good byte sequences

The udev rule (udev/70-wscanfd.rules) gives the plugdev group access:

SUBSYSTEM=="usb", ATTRS{idVendor}=="04d8", ATTRS{idProduct}=="0053", MODE="0660", GROUP="plugdev"

Install the rule only if you use the userspace driver. The kernel driver doesn't need it. Raw USB access lets a user transmit arbitrary frames on both buses, detach the kernel driver and send the firmware-update command (0x8006). The rule therefore doesn't grant it to whoever is logged in (no uaccess tag). Add the users you trust with the bus to plugdev instead (sudo usermod -aG plugdev <user>, then log in again).

If wscanfd.ko is bound to interface 0, the userspace driver detaches it on open. Use one driver or the other, not both.

5.3 SocketCAN bridge (vcan)

sudo modprobe vcan
sudo ip link add dev vcan0 type vcan && sudo ip link set vcan0 mtu 72 up   # mtu 72 = CAN FD capable
.venv/bin/python -m wscanfd bridge -c 0 -b 250000 -d 2000000 -i vcan0
candump vcan0           # in another terminal; cansend / python-can / Wireshark also work

Frames received on the bus appear on vcan0, and frames written to vcan0 are transmitted on the bus. The bridge opens a CAN_RAW socket with CAN_RAW_FD_FRAMES and converts between struct can_frame/canfd_frame and the adapter formats. Error frames written to the socket are ignored.

Bitrate and mode come from the bridge's command line, not from ip link, because a vcan interface has no bit timing. Configuring with ip link needs the kernel driver.

5.4 Python API

from wscanfd.device import USBCANFD
from wscanfd.protocol import Frame

with USBCANFD() as dev:                       # open: claim, drain, open handshake, device info
    print(dev.info)                           # serial=USBCANFD2024... hw=2.00 fw=2.12

    dev.send(Frame(0x1ABCDEF0, bytes(20), extended=True, fd=True, brs=True, channel=0))
    f = dev.recv(timeout=1.0)                 # Frame or None
    if f:
        print(f, f.timestamp_us)

The driver logs Waveshare USB-CAN-FD serial … hw 2.00 fw 2.12 at probe and one line per channel (channel CAN1/CAN2). netdev->dev_port is set to the channel index, so udev rules can name the interfaces stably. Listen-only mode is listen-only on, and classic-only operation is fd off.

Recommended settings

  • For CAN FD with BRS, use sample-point 0.8, or more generally the same nominal sample point as every other node on the bus. The kernel's default (87.5 % at 250k/500k, 75 % at 1M) differs from the 80 % that most FD nodes use, and BRS frames then fail (see the box below). The default data-phase sample point is fine.
  • Classic CAN: the kernel defaults work (18/18 at 250k).
  • txqueuelen 1000 is fine for bursty senders. The driver paces frames into the adapter itself, so a long netdev queue just holds frames back and does not overflow the adapter: sudo ip link set can1 txqueuelen 1000.
  • Termination: set the physical switch. There is no software control.

Why BRS needs the same nominal sample point on every node

Each node switches to the data bit rate at its own nominal sample point in the BRS bit. With the kernel default of 87.5 % at 500k against the peer's 80 %, the two switch points are 7.5 % of a 2 µs bit apart, which is 150 ns, or about 30 % of a 2 Mbit/s data bit. The adapter's data-phase resynchronisation (data SJW about 50 ns) cannot absorb that. On the bench, BRS frames from the peer failed CRC at the adapter: only 25 of 82 round trips passed, the peer went error-passive, and its TX FIFO blocked. With sample-point 0.8 on the adapter, 82/82 passed. CiA 601-3 recommends 80 % and identical sample points across all nodes.

Module parameters

All are mode 0644 and can be changed at runtime, for example echo 2 | sudo tee /sys/module/wscanfd/parameters/tx_dev_queue, or set at load time with insmod kernel/wscanfd.ko idle_poll_us=500.

6.2 Design

  • Binding: USB 04d8:0053, interface 0, after checking that bulk endpoints 0x01, 0x81, 0x82 and 0x83 exist. It creates two netdevs: can0 = board CAN1 (protocol channel 0, RX EP 0x82) and can1 = board CAN2 (channel 1, RX EP 0x83).
  • Probe: drain EP 0x81, send the open challenge (0x8001; the reply is not validated), read device info (0x8005) and log it. It never sends SET_CONFIGURATION. If the open command gets no reply, probe fails with a hint that the device may need a power cycle.
  • Commands: synchronous usb_bulk_msg() on EP1 OUT, then on EP 0x81, under a mutex, with a 3 s timeout. Replies with a different cmd (late replies to an earlier, timed-out command) are skipped, up to 4 of them. On any error, EP1 IN is drained, and failures are logged with rate limiting.
  • ndo_open: InitCAN (0x8002) with timing words computed from the kernel's can_bittiming (BRP−1, SJW−1, prop_seg + phase_seg1 − 1, phase_seg2 − 1), clear the filter (0x800B), drain stale records from the RX endpoint, StartCAN (0x8003), then submit the RX URBs. In FD mode the dbit word comes from the data bittiming; otherwise the default 0x03030A02 is sent. Byte 30 = 0x80 for fd-non-iso on.
  • ndo_stop: stop the queue, cancel the timers, kill the RX and TX URBs, send ResetCAN (0x8009). Disconnect / rmmod unregisters the netdevs and sends CloseDevice (0x800A). soft_unbind keeps the device reachable for that last command.
  • RX: 2 bulk-IN URBs per channel with 4096-byte buffers. A completion carrying records is parsed and resubmitted immediately. An idle poll (8 zero bytes) re-arms through an hrtimer after idle_poll_us (1 ms), which gives about 1940 USB interrupts/s per open idle channel. FD records are dropped while the interface is fd off, because the controller always runs FD-capable. -EPIPE schedules a work item that calls usb_clear_halt(). Other errors and failed resubmits retry after 10 ms, so RX never silently dies.
  • TX: one async bulk URB per frame on EP1 OUT (cmd 0x8004, channel byte in the payload), with up to 16 echo slots. Only classic and FD skbs are accepted (CAN XL is dropped). FD lengths are rounded up to valid DLC lengths and zero-padded. Admission is limited by the device-queue model (6.3).
  • Echo (IFF_ECHO): released when the TX URB completes, which means "accepted by the adapter". No bus-level confirmation exists. tx_bytes/tx_packets are counted by the driver itself.
  • Bus state: always ERROR-ACTIVE. There is no do_set_mode/restart support, because the firmware never reports bus-off or any live error state.
  • ctrlmodes: LISTENONLY, FD, FD_NON_ISO. Termination is a physical switch.

6.3 TX pacing: the device-queue model

The firmware has no TX flow control (quirks). It buffers only about 10 frames, keeps completing USB writes when it is full, and drops the excess silently. A naive driver that submits as fast as USB accepts lost 1950 of a 2000-frame burst. The driver therefore models the adapter's queue:

  1. For each frame, estimate the time on the wire: can_frame_bits() with worst-case stuffing × the nominal bit time. For FD + BRS, the arbitration bits are counted at the nominal rate plus data bits × 1.25 at the data rate. Add 10 %, with a floor of tx_min_frame_us + 2 µs per data byte.
  2. Keep a per-channel ring of estimated wire-finish times. Each new frame finishes at max(now, previous finish) + its frame time.
  3. Received frames count too. Each RX frame (on either channel) pushes the TX finish estimates of both channels back by tx_min_frame_us + 2 µs × payload, because the firmware spends that time handling it. Without this, TX under a 1:1 echo load needed about twice the per-frame floor and lost frames.
  4. When tx_dev_queue frames are "inside" the adapter, stop the netdev queue and arm an absolute-time hrtimer for the oldest frame's finish time. When it fires, expire finished frames and wake the queue.
  5. Also keep at most tx_dev_queue USB transfers in flight per channel. Transfers normally complete in about 1 ms, so this costs no throughput. It limits the backlog that queues behind EP1 OUT when the firmware stops reading it (see below).

With this, 500-frame bursts under a 1:1 echo load are lossless in both directions, and the adapter's RX itself was lossless under that load.

Limitation: if other nodes take a lot of bus time, the adapter drains slower than the model assumes. Allowing 4 of the about 10 buffer slots tolerates roughly a 2.5× slowdown. On a busy bus, lower tx_dev_queue.

Limitation: Unacknowledged frames stall both channels: all TX shares EP1 OUT, and the firmware stops reading it while it retries an unacknowledged frame. With can0 sending into a bus with no other node, can1 dropped from about 195 to about 5 frames/s, and after a 3 s burst on can0, can1 waited about 12 s for its next frame (18 s before the driver capped in-flight transfers). Don't transmit on a channel that has no other node on its bus.

7. Test rig & results

7.1 Bench rig

The peer node is a LilyGo T-2CAN-FD (ESP32-S3) running the project's t2can-echo/ firmware (ESP-IDF). It has two CAN ports:

  • CAN A: MCP2518FD (CAN FD) on SPI (SCLK 12, MOSI 11, MISO 13, CS 10), driven by a minimal register-level polling driver (mcp2518fd.c). Used for all FD tests and the bitrate sweep.
  • CAN B: ESP32 TWAI (classic only, TX GPIO 7 / RX GPIO 6), fixed at 250 kbit/s. Used for the first classic-CAN tests.

Both ports echo every received frame with ID + 1 and data XOR 0xFF, keeping the length and the FD/BRS/IDE flags. CAN A can also send a 1 Hz heartbeat on ID 0x7E0. The PC drives the peer through its USB Serial/JTAG console. tools/t2can_console.py logs the console to a file and forwards commands written to a FIFO, so test scripts can change the peer's bitrate mid-run.

Peer-board findings worth knowing

  • The T-2CAN-FD's MCP2518FD runs from a 40 MHz clock (OSC = 0x460: no PLL, no divider). LilyGo's Longan_CANFD example defaults to MCP2518FD_20MHz, so its bit timing is wrong by a factor of 2.
  • ESP32-S3 SPI without DMA is limited to 64 bytes per transaction, so 64-byte FD frames need SPI_DMA_CH_AUTO.
  • 500k/3M cannot be produced by the 40 MHz MCP2518FD, so that combination is untested, not failed.

7.4 Error behaviour

tools/status_probe.py provokes error conditions through the peer (it stops ACKing, or runs the peer at the wrong bitrate) while polling 0x800D. Findings:

  • No error or status records appear on the RX endpoints, and TX never gets a completion or failure reply.
  • Unacknowledged frames are retried (about 2000 attempts, about 0.5 s, at 500k) and then silently dropped. Afterwards the channel recovers by itself.
  • Unacknowledged frames stall both channels: all TX shares EP1 OUT, and the firmware stops reading it while it retries an unacknowledged frame. With can0 sending into a bus with no other node, can1 dropped from about 195 to about 5 frames/s, and after a 3 s burst on can0, can1 waited about 12 s for its next frame (18 s before the driver capped in-flight transfers). Don't transmit on a channel that has no other node on its bus.
  • 0x800D showed TEC = 128 and CEL = 128 during a no-ACK episode, but the values froze, and TEC read 0 while the adapter was still retransmitting. It is a stale snapshot.

For drivers this means: deliver the TX echo when the adapter accepts the frame (or disable IFF_ECHO), report ERROR_ACTIVE, use 0x800D only as a hint, and pace TX (quirks). The kernel driver does all of this.
